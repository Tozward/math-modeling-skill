# 跨账号接力协议

本协议用于在不同 Codex 会话、ChatGPT 账号或参赛队员设备之间恢复数学建模项目状态。

它只负责项目连续性，不改变本 Skill 原有的三个角色、五个阶段门禁或固定交付物。

## 一、核心原则

1. 项目文件是权威状态，对话历史不是权威状态。
2. `SKILL_ROOT` 始终只读，由本次实际加载的根 `SKILL.md` 确定；不得假设固定绝对路径。所有接力状态只写入 `PROJECT_ROOT`。
3. 原有固定门禁仍只有：
   - `M1`
   - `P1`
   - `P2`
   - `W1`
   - `W2`
4. 换账号、换会话或换设备本身不会使已经通过的门禁失效。
5. 只有被某门禁验收的输入或产物发生实质变化时，该门禁才变为 `STALE` 并需要复验。
6. 已完成且仍有效的阶段不得仅因为新会话不了解历史而重复执行。
7. 对话深度链接可以作为人工追溯材料，但不得成为恢复项目所必需的依赖。
8. 接力状态属于内部工作信息，严禁写入正式数学建模论文正文、摘要、结论或官方要求的论文附录。

## 二、权威状态文件

启用跨账号模式后，`PROJECT_ROOT` 中维护：

- `AGENTS.md`
- `CURRENT_TASK.md`
- `DECISIONS.md`
- `HANDOFF.md`
- `AI使用日志.md`

以及：

- `.handoff/SKILL.lock`
- `.handoff/GATE_STATE.json`
- `.handoff/ACTIVE_WORK.json`
- `.handoff/gate-evidence/`

职责严格区分：

### `AGENTS.md`

稳定的项目运行协议。

只记录：
- `SKILL_ROOT` 的解析与使用方式；
- 恢复顺序；
- 项目写入边界；
- 门禁连续性规则；
- 决策连续性规则。

不得记录易变的当前任务进度。

### `CURRENT_TASK.md`

当前项目状态的单一事实源。

只保留：
- 当前阶段；
- 当前目标；
- 已完成门禁；
- 相关决策 ID；
- 权威输入；
- 权威输出；
- 已知问题；
- `Next Action`；
- `Do Not Redo`。

保持简洁，不承担历史日志功能。

### `DECISIONS.md`

重要人工/团队决策的 append-only 日志。

旧决策不得静默改写。

需要推翻旧决策时，新建决策并通过 `Supersedes` 指向旧决策。

### `HANDOFF.md`

只记录最近一棒交接发生了什么：

- 本棒完成内容；
- 新发现；
- 未完成事项；
- 下一账号首先执行的动作；
- Git HEAD。

不得复制完整 `CURRENT_TASK.md`。

### `AI使用日志.md`

按时间追加 AI 使用事实记录。

至少记录：
- 时间；
- 操作队员；
- AI 工具/模型；
- 使用阶段；
- 主要提示方式；
- AI 主要输出；
- 实际采纳；
- 人工修改；
- 人工验证。

不得在赛后凭空补造未发生的 AI 使用过程。

## 三、机器状态

### `.handoff/SKILL.lock`

记录比赛项目所绑定的 Skill 版本。

至少包含：

- schema version；
- upstream `VERSION`；
- Skill Git commit。

Skill 的绝对安装路径不参与一致性判定。

不同设备可以把 Skill 安装在不同位置；
handoff 始终使用本次实际加载的 `SKILL_ROOT`。

同一比赛项目的队员应使用完全相同的 Skill commit。

### `.handoff/GATE_STATE.json`

保存五个固定门禁的机器可读状态。

允许状态：

- `NOT_STARTED`
- `PENDING`
- `PASS`
- `FAIL`
- `BLOCKED`
- `STALE`

`PASS` 至少记录：

- 验收时项目 Git commit；
- 被验收产物；
- 各产物 SHA-256；
- gate evidence 路径。

若已记录 SHA-256 的产物后来发生变化，则该 `PASS` 不再有效，应报告 `STALE`。

### `.handoff/ACTIVE_WORK.json`

保存当前正在执行的原子工作。

这是 write-ahead recovery record，
用于防止模型、客户端、网络或账号额度意外中断导致高成本推理状态全部丢失。

允许状态：

- `IDLE`
- `IN_PROGRESS`

`IN_PROGRESS` 至少记录：

- work ID；
- 当前 stage；
- objective；
- atomic unit；
- next action；
- 输入；
- 预期输出；
- 开始时项目 Git HEAD；
- checkpoint 数量；
- 最近 checkpoint；
- 涉及文件及可用哈希。

较大的语义工作必须先 `begin-work`，
再开始昂贵推理。

出现有意义的中间进展后使用 `checkpoint`。

原子工作真正结束后使用 `finish-work`。

它不是新的 Gate，
也不替代 M1/P1/P2/W1/W2。

### `.handoff/gate-evidence/`

保存 M1/P1/P2/W1/W2 的独立验收回执。

其内容属于内部质检信息，不得进入正式论文。

## 四、新会话恢复顺序

新 Codex 会话或新账号接手时：

1. 读取 `AGENTS.md`。
2. 从当前实际加载的根 `SKILL.md` 确定 `SKILL_ROOT`。
3. 运行确定性的 handoff 检查。
4. 读取 `.handoff/ACTIVE_WORK.json`。
5. 若为 `IN_PROGRESS`，保留 working tree，并从其中的 `next_action` 恢复当前 atomic unit。
6. 若上一工作已 finish 但尚未建立后续 Git checkpoint，先完成持久化收尾。
7. 读取 `CURRENT_TASK.md`。
8. 读取 `.handoff/GATE_STATE.json`。
9. 读取 `HANDOFF.md`。
10. 只读取 `CURRENT_TASK.md` 明确引用的 `DECISIONS.md` 条目。
11. 按当前阶段渐进式加载对应角色 `SKILL.md`。
12. 继续当前原子工作或项目级 `Next Action`。

不得仅因为对话历史缺失而：

- 重做已完成的题意分析；
- 重新选择已经冻结的模型；
- 重新运行仍有效的 M1/P1/P2/W1/W2；
- 重新生成仍有效的结果或论文。

## 五、门禁连续性

跨账号接力不新建任何 Gate。

仍使用：

`M1 → P1 → P2 → W1 → W2`

每个门禁的验收语义继续由 `references/Subagent调度.md` 定义。

跨账号层只负责持久化：

- 状态；
- evidence；
- artifact hash；
- validated commit。

主 Agent 不得自行把质检 Subagent 的 `FAIL` 改写为 `PASS`。

## 六、抢占安全原则

系统不得假设一次高强度模型调用一定能正常结束。

对于重新执行会明显浪费推理额度的语义工作：

1. 先 `begin-work`；
2. 再开始深度推理；
3. 在语义边界执行 `checkpoint`；
4. 原子工作完成后执行 `finish-work`；
5. 重要原子工作结束或准备接力时建立本地 Git checkpoint。

checkpoint 按语义进展触发，
不按固定分钟数触发。

如果新账号发现 `IN_PROGRESS`：

- 不得覆盖 ACTIVE_WORK；
- 不得清理 dirty tree；
- 不得仅因为聊天历史缺失而重新开始该阶段；
- 应检查 checkpoint、touched files 和实际文件后继续。

如果中断发生在 `finish-work` 后而 Git checkpoint 前，
应先完成该工作单元的持久化收尾。

`ACTIVE_WORK` 只负责短期恢复，
`CURRENT_TASK.md` 负责较稳定的项目级状态，
两者不得互相复制成冗长日志。

---

## 六、检查点原则

完成重要阶段后应建立本地 Git checkpoint。

推荐：

- `M1 PASS` 后；
- `P1 PASS` 后；
- `P2 PASS` 后；
- `W1 PASS` 后；
- `W2 PASS` 后；
- 重要模型决策发生变化后；
- 准备换账号前。

比赛项目的 Git 可仅作为本地版本控制使用，不要求设置远程仓库。

## 七、传输边界

本 Skill 不负责：

- ZIP 压缩；
- 云上传；
- 微信发送；
- AirDrop；
- U 盘复制；
- 网络文件传输。

项目传输由参赛队员人工完成。

传输时必须保留：

- 项目实际文件；
- `.git/`
- `.handoff/`

否则无法保证完整恢复 Git 历史和门禁状态。

## 八、额度节约原则

可以由确定性程序完成的检查，不交给语言模型重复推理，包括：

- Git HEAD；
- working tree 状态；
- 文件是否存在；
- SHA-256；
- Skill commit 一致性；
- JSON schema；
- PASS 产物是否发生变化。

模型只负责语义性工作和原 Skill 已规定的独立质检。

本协议的目的之一，是使新账号仅加载完成当前任务真正需要的最小上下文。
